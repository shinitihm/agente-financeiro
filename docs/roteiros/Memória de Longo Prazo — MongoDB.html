MemorySaver e MongoDB trabalham juntos

O MemorySaver continua no grafo — garante que o LLM lembre do contexto dentro da conversa atual. O MongoDB é a camada extra: persiste tudo em disco para que sessões futuras possam consultar o histórico.

// 01 — o problema

Por que o MemorySaver não é suficiente?

O MemorySaver guarda o histórico em RAM. Ele resolve a memória de curto prazo — o modelo lembra do que foi dito dentro da mesma execução. Mas quando o processo reinicia, tudo se perde.

Para um assessor financeiro real, isso é inaceitável. O usuário registrou um Pix na segunda-feira — na quinta, o sistema não pode ter esquecido.

// 02 — modelagem

Um documento por sessão

A escolha foi um documento MongoDB por conversa completa. Cada sessão tem seu próprio doc, identificado por um UUID. O session_id é o identificador do usuário — pode ser um ID de Telegram, número de telefone, qualquer string única.

Por que o _id é um UUID?

Dois motivos. Primeiro: o mesmo usuário pode ter múltiplas sessões ao longo do tempo — se o session_id fosse o _id, o segundo documento do mesmo usuário colidiria no MongoDB.

Segundo, e mais importante para o futuro do projeto: nas próximas aulas vamos usar o Qdrant como banco vetorial para busca semântica sobre o histórico. O Qdrant exige que os IDs dos seus vetores sejam UUIDs. Ao usar o mesmo UUID como _id no MongoDB e como ID no Qdrant, os dois bancos ficam sincronizados — dado um vetor no Qdrant, você sabe exatamente qual documento buscar no MongoDB.

MongoDB _id = Qdrant point ID

O UUID gerado em iniciar_sessao() vai ser o mesmo em ambos os bancos. Isso elimina a necessidade de uma tabela de mapeamento extra entre eles.

Estrutura do documento

{
  "_id": str,        // UUID — mesmo ID que será usado no Qdrant
  "session_id": str,        // ID do usuário — vem do main.py
  "iniciada_em": datetime,   // quando a sessão começou
  "atualizada_em": datetime,   // atualizado a cada mensagem
  "resumo": str,        // gerado pelo LLM ao encerrar — vazio durante a sessão
  "mensagens": list[dict], // array crescente de mensagens
}

// cada item de "mensagens":
{ "role": "human" | "assistant", "content": "..." }

Índices criados automaticamente

Dois índices são criados na inicialização do módulo. Tornam as consultas por usuário e por data eficientes, mesmo com milhares de sessões.

memory_mongodb.py python 
col_sessoes.create_index("session_id")   # busca por usuário
col_sessoes.create_index("iniciada_em")  # ordenar por data
// 03 — as três funções

API pública do módulo

O módulo expõe exatamente três funções. Tudo que o main.py precisa saber está aqui — conexão, UUID e estado interno são detalhes escondidos dentro do arquivo.

iniciar_sessao(session_id)

Cria um documento novo no MongoDB. Gera o UUID e registra o mapeamento session_id → doc_id no dicionário interno.

retorna → None
salvar_mensagem(session_id, role, content)

Adiciona uma mensagem ao array mensagens do documento ativo via $push. Atualiza o campo atualizada_em.

retorna → None
encerrar_sessao(session_id)

Carrega as mensagens do Mongo, chama o LLM para gerar o resumo, salva no documento e remove a sessão do estado interno.

retorna → str (resumo gerado)

O estado interno — e sua limitação

Dentro do módulo existe um dicionário _sessoes_ativas que mapeia session_id → doc_id. Ele existe porque o main.py nunca precisa conhecer o UUID — só o session_id.

Limitação para a aula

O _sessoes_ativas vive na RAM. Se o processo reiniciar entre o iniciar_sessao e o salvar_mensagem, o mapeamento se perde e o salvar_mensagem vai lançar KeyError. Para produção, esse estado deveria ir para o próprio MongoDB. Para a aula de persistência, é suficiente.

// 04 — entendendo o memory_mongodb.py

Explicação dos trechos principais

1. iniciar_sessao — criando o documento

A função gera o UUID, monta o documento com campos vazios e faz o insert_one. O _id do MongoDB recebe o UUID diretamente — o mesmo que será usado no Qdrant no futuro.

memory_mongodb.py python 
def iniciar_sessao(session_id: str) -> None:
    doc_id = str(uuid.uuid4())   # mesmo ID que irá para o Qdrant
    agora  = _agora()

    col_sessoes.insert_one({
        "_id":           doc_id,
        "session_id":    session_id,
        "iniciada_em":   agora,
        "atualizada_em": agora,
        "resumo":        "",
        "mensagens":     [],
    })

    _sessoes_ativas[session_id] = doc_id

2. salvar_mensagem — $push no array

Em vez de fazer find → append → save, usamos o operador $push do MongoDB. Ele adiciona um item ao array diretamente no banco — uma única operação atômica, sem risco de sobrescrever dados.

memory_mongodb.py python 
def salvar_mensagem(session_id: str, role: str, content: str) -> None:
    doc_id = _sessoes_ativas[session_id]

    col_sessoes.update_one(
        {"_id": doc_id},
        {
            "$push": {"mensagens": {"role": role, "content": content}},
            "$set":  {"atualizada_em": _agora()},
        },
    )

3. encerrar_sessao — resumo via LLM

Ao encerrar, o módulo carrega as mensagens do Mongo, formata como texto e passa para o LLM gerar um resumo conciso. O resumo é salvo de volta no documento — permite consultas futuras sem precisar reler todas as mensagens.

memory_mongodb.py python 
def encerrar_sessao(session_id) -> str:
    doc_id = _sessoes_ativas.get(session_id)
    if not doc_id:
        return ""

    doc = col_sessoes.find_one({"_id": doc_id})

    if not doc or not doc.get("mensagens"):
        _sessoes_ativas.pop(session_id, None)
        return ""   # sessão vazia — nada a resumir

    resumo = _gerar_resumo(doc["mensagens"])

    col_sessoes.update_one(
        {"_id": doc_id},
        {"$set": {"resumo": resumo, "atualizada_em": _agora()}},
    )

    _sessoes_ativas.pop(session_id)
    return resumo

4. _formatar_conversa — preparando o texto para o LLM

Antes de chamar o LLM de resumo, as mensagens precisam virar texto. A função usa o role diretamente — consistente com como salvamos ("human" e "assistant").

memory_mongodb.py python 
def _formatar_conversa(mensagens: list[dict]) -> str:
    linhas = []
    for msg in mensagens:
        linhas.append(f"{msg['role']}: {msg['content']}")
    return "\n".join(linhas)

# o LLM de resumo recebe algo assim:
# human: quero registrar um pix de R$50 para o João
# assistant: Pix de R$50 registrado com sucesso!
# human: e um evento amanhã às 14h com o cliente Silva
# assistant: Evento agendado para amanhã às 14h.
// 05 — o que vai no main.py

Os pontos de integração

Vocês vão receber o memory_mongodb.py pronto. A tarefa é entender o módulo e adicionar as chamadas no main.py nos lugares certos.

  • 01
    Import das três funções + anonimizar_entrada

    from memory_mongodb import iniciar_sessao, salvar_mensagem, encerrar_sessao e from guardrail import anonimizar_entrada. Sem isso, o Python não encontra as funções.

  • 02
    Chamar iniciar_sessao antes do loop

    Antes de entrar no while True, chamar iniciar_sessao(session_id). Cria o documento no MongoDB. Sem essa chamada, o salvar_mensagem vai lançar KeyError porque o mapeamento ainda não existe.

  • 03
    Anonimizar antes do grafo e salvar a versão limpa

    Dentro de executar_fluxo_assessor, chamar anonimizar_entrada(pergunta_usuario) antes de invocar o grafo. O resultado anonimizado é o que vai para o Mongo — não a mensagem original com PII. O grafo continua recebendo a mensagem original normalmente e faz sua própria anonimização internamente.

  • 04
    Chamar encerrar_sessao ao sair

    No bloco que detecta o comando de saída, chamar encerrar_sessao(session_id). Ela gera o resumo e persiste no documento. O retorno é o texto do resumo — pode ser impresso para o usuário.

main.py — os trechos que precisam existir python 
# ── IMPORTS ─────────────────────────────────────────────────────
from memory_mongodb import iniciar_sessao, salvar_mensagem, encerrar_sessao
from guardrail      import anonimizar_entrada


# ── DENTRO DE executar_fluxo_assessor() ─────────────────────────
def executar_fluxo_assessor(pergunta_usuario: str, session_id: str) -> str:

    # anonimiza aqui para ter a versão limpa disponível para salvar
    texto_anonimizado, _ = anonimizar_entrada(pergunta_usuario)

    estado_inicial = {
        "messages":         [{"role": "human", "content": pergunta_usuario}],
        "agentes_chamados": [],
        "rota":             "",
        "mapa_pii":         {},
    }

    estado_final = fluxo_agentes.invoke(
        estado_inicial,
        config={"configurable": {"thread_id": session_id}},
    )

    resposta = estado_final["messages"][-1].text

    salvar_mensagem(session_id, "human",     texto_anonimizado)
    salvar_mensagem(session_id, "assistant", resposta)

    return resposta


# ── LOOP PRINCIPAL ───────────────────────────────────────────────
session_id = "id_usuario"
iniciar_sessao(session_id)   # ← obrigatório antes do loop

while True:
    user_input = input("> ")
    if user_input.lower() in ("sair", "fim", "tchau"):
        resumo = encerrar_sessao(session_id)
        if resumo:
            print(f"Resumo da sessão: {resumo}")
        print("Até logo!")
        break

    resposta = executar_fluxo_assessor(user_input, session_id)
    print(resposta)
Por que anonimizar duas vezes?

O grafo já tem o no_guardrail_entrada que anonimiza internamente. Mas esse resultado fica dentro do estado do LangGraph — não é acessível de fora sem adicionar uma chave nova no estado. A solução mais simples é chamar anonimizar_entrada() uma vez antes do grafo: o texto_anonimizado fica disponível para salvar no Mongo, e o grafo faz sua própria anonimização normalmente. A função é determinística, então o resultado é idêntico nas duas chamadas.
